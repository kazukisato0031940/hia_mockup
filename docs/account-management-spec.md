# 第1部　アカウント発行

> 「アカウント発行」とは、ある健保・企業を本システムで扱えるようにするための一連の初期登録（組織階層の登録、コードの整備、加入者データの取込・紐づけ）を指す。

## 1. 管理する階層

### 1.1 階層構造

```
運営会社（システム全体）
  └─ 健康保険組合        … 保険者番号・名称で識別
       └─ 企業           … 「事業所（企業）コード」で識別（健保が管理）
            └─ 事業所     … 「所属コード」で識別（企業が管理）
                 └─ 部署  … 「部署コード」で識別（企業が管理）
                      └─ 加入者
```

- 上位の階層に属さない下位階層は作れない（部署は必ず事業所配下、事業所は必ず企業配下、企業は必ず健保配下）。
- **部署**は事業所の下の階層。企業・事業所ごとに登録する。
- ログインアカウント（管理者）と加入者は、いずれも階層のいずれかに紐づく末端データだが、性質が異なる（管理者＝操作者、加入者＝管理対象）。

### 1.2 加入者の所属は後追いでよい

- 加入者は、**事業所・部署が未設定のままでも登録できる**。
- 未設定・未紐づけの加入者は、あとから企業・事業所・部署へ紐づけられる（第3節参照）。
- 既存データを本システムへ移行する場合、移行時の紐づけ状態はそのまま引き継ぐ。

### 1.3 各階層の登録手段

| 階層 | 画面からの個別登録 | CSV一括取込 | 実行できるロール |
|---|---|---|---|
| 健康保険組合 | 可 | 不可 | 運営会社スタッフのみ |
| 企業 | 可 | 可（企業登録フォーマット） | 運営会社スタッフ・健保担当者 |
| 事業所 | 可 | 可（企業登録／事業所登録フォーマット） | 操作範囲内の企業を持つロール |
| 部署 | 可 | （企業登録フォーマットで事業所行と同時に扱う） | 操作範囲内の企業を持つロール |
| 加入者 | 可 | 可（加入者情報フォーマット） | 操作範囲内のロール |

---

## 2. コードの持ち方

### 2.1 方針

企業・事業所・部署は、**2種類のコードを併存**させる。

| 種別 | 誰が決めるか | 用途 | 例 |
|---|---|---|---|
| 外部コード | 健保・企業（先方） | **取込時の照合・更新キー**。加入者CSVの所属指定にも使う | 企業「456」 |
| 内部コード | 本システムが自動採番 | 画面表示・並び順・一意識別 | 企業「C59086CC」 |

- 従来運用の課題（先方の番号と運営会社の番号が別で、加入者データを取り込んでも所属先に結びつかない／同じファイルを取り込むたびに重複が増える）を解消するために、**先方の番号をそのまま保持し照合キーにする**。

### 2.2 外部コード

| 階層 | 外部コードの名称 | 管理主体 |
|---|---|---|
| 企業 | 事業所（企業）コード | 健保 |
| 事業所 | 所属コード | 企業 |
| 部署 | 部署コード | 企業 |

- 外部コードは**任意入力**。空欄でも登録できる。
- 外部コードが空欄の場合、取込時の照合は**名称**（企業名／事業所名）で行う。
- 外部コードは取込のたびに保存・更新され、次回以降の照合キーになる。

### 2.3 内部コード

| 階層 | 採番規則 | 特性 |
|---|---|---|
| 企業 | 「健保名＋企業名」から決定的に生成（名称を正規化して法人格語などを除去したうえで生成）。先頭に識別文字＋固定桁数（例：`C` ＋ 7桁）| **同じ健保名・企業名なら常に同じコード**。企業情報を更新してもコードは変わらない |
| 事業所 | 登録順の連番（例：001, 002 …） | 企業内で一意 |
| 部署 | 登録順の連番（例：001, 002 …） | 事業所内で一意 |

- 内部コードはシステムが割り振るため、CSVにその列があってもファイルの値は使わない。

### 2.4 表示・並び順

- 画面表示および並び順は「**外部コードがあれば外部コード、なければ内部コード**」を用いる。

## 3. CSV一括取込

### 3.1 取込フォーマット（3種類）

| フォーマット | 列数 | 用途 | 1行の単位 | 必須項目 |
|---|---|---|---|---|
| 企業登録フォーマット | 12 | 企業と事業所をまとめて登録・更新 | 企業＋事業所 | 保険者番号／企業名／事業所名 |
| 事業所登録フォーマット | 8 | 既存企業へ事業所を追加・更新 | 事業所 | 保険者番号／事業所（企業）コード／事業所名 |
| 加入者情報フォーマット | 23 | 加入者（本人・家族）を登録・更新 | 加入者1名 | 被保険者証番号／対象者氏名（漢字） |

補足：
- 保険者番号でどの健保に取り込むかを指定する（運営会社スタッフのみ。健保担当者・企業担当者は自分の所属健保に固定）。
- 加入者情報フォーマットでは、企業は「事業所（企業）コード」、事業所は「所属コード」で所属先を指定する（外部コード・内部コードのどちらでも引ける）。
- **本人と家族の区別**は「被保険者証番号＋被保険者証枝番」で行う（同一番号・別枝番）。
- 採番対象の項目（加入者ID、事業所の内部コード 等）は、ファイルに値があっても使わず、システムが採番する。

### 3.2 文字コード・データ形式

- 取込ファイルの文字コードは **UTF-8 / Shift_JIS を自動判別**。判別できない場合はエラーとして取り込まない。
- ダウンロード（フォーマット・出力）は Shift_JIS（Excel でそのまま開ける形式）。
- 日付は `YYYY/MM/DD`・`YYYY-MM-DD` などの区切りを許容し、内部の標準形式へ正規化する。正規化できない値はエラー行とする。

### 3.3 照合・更新（冪等性）

各階層は次のキーで既存レコードを照合する。**一致すれば更新、なければ新規登録**。

| 階層 | 照合キー（上から順に試す） |
|---|---|
| 健康保険組合 | 保険者番号 |
| 企業 | (健保, 事業所（企業）コード) → (健保, 企業名) |
| 事業所 | (企業, 所属コード) → (企業, 事業所名) |
| 加入者 | (健保, 被保険者証記号, 被保険者証番号, 被保険者証枝番) |

- この照合により、**同じCSVを何度取り込んでも重複が発生しない**（毎月同形式で届くファイルをそのまま再取込できる）。

### 3.4 取込順序の独立性

- 企業・事業所より先に**加入者データだけが届いても取り込める**。
- 取込時、加入者行の「事業所（企業）コード」「所属コード」は加入者側に保持され、所属先が未登録なら**「未紐づけ」状態で登録**する（警告として提示、エラーにはしない）。
- あとから企業・事業所を登録したうえで、保持しておいたコードを使って**まとめて紐づけ**られる（下記 3.6）。

### 3.5 取込フロー（検証プレビュー付き）

```
1. フォーマット（またはサンプル）をダウンロードして内容を確認
2. ファイルを指定（画面へドラッグ＆ドロップ）
3. システムが全行を検証し、プレビューを表示
      ・行ごとに「新規 / 更新」の別
      ・警告（未登録コードを未紐づけで登録する 等）
      ・エラー（必須未入力、日付形式不正、健保が操作範囲外 等）
      ・エラーが1行でもあれば、確定は不可
4. 内容を確認して「確定」
5. 一括登録・更新を実行
```

- ファイル内で同一の企業・事業所・加入者を指す行が重複している場合はエラーとする。
- 取込の検証・確定は、件数・ファイル名とともに監査ログに記録する。

### 3.6 未紐づけ加入者のまとめて紐づけ（概要）

第1部の締めくくりとして、未紐づけ加入者を所属先へ結びつける操作を用意する。詳細仕様は本書のスコープ外だが、要点は次のとおり。

- 加入者一覧の**検索結果を対象に、複数件をまとめて**企業→事業所→部署に紐づけられる（1件ずつ開く必要がない）。
- 選択方法：行チェック／表示中すべて／検索条件に一致する全件。
- 取込ファイルに含まれていたコードから所属先を**自動判定して紐づける**方法も用意する。
- 紐づけ結果は一覧に即時反映し、操作ログに残す。

|---|---|---|

# 第2部　ログインアカウントの管理

> 健保管理システム（健保担当者・企業担当者が使う画面）における、ログインアカウントの発行・変更・停止・削除と権限設定の仕様。
> 運営会社スタッフ（`system_admin`）のアカウントは「総合管理」画面側で管理するため、ここでは対象ロールとしてのみ言及する。

## 5. ロール

| ロールキー | 表示名 | 主な利用者 | 既定の閲覧範囲 |
|---|---|---|---|
| `system_admin` | 当社スタッフ | 運営会社 | 全健保 |
| `kenpo_user` | 健保担当者 | 健保 | 自組合全体 |
| `company_user` | 企業担当者 | 企業 | 担当範囲のみ |

### 5.1 発行可能ロール（自分より上位の権限は付与できない）

| 操作者ロール | 新規発行・変更で指定できるロール |
|---|---|
| `system_admin` | `system_admin` / `kenpo_user` / `company_user` |
| `kenpo_user` | `kenpo_user` / `company_user` |
| `company_user` | `company_user` のみ |

- 権限外のロールを指定した場合はエラーとし、監査ログに「ブロック」として記録する。

## 6. 閲覧範囲（自動決定）

閲覧範囲は**ロールから自動的に決まり、画面で手動指定させない**。

| 閲覧範囲キー | 表示名 | 決定条件 | 見える加入者 |
|---|---|---|---|
| `all` | 全健保 | ロール = `system_admin` | すべての健保の加入者 |
| `kenpo_all` | 自組合全体 | ロール = `kenpo_user` | 所属健保に属する全企業の加入者 |
| `own_company` | 担当する範囲 | ロール = `company_user` | 「担当範囲」に含まれる加入者のみ |

## 7. 担当範囲（`company_user` のみ）

`company_user` は「担当範囲」を持つ。担当範囲は**企業・事業所・部署の3階層を横断**して、複数を任意に組み合わせて指定できる。

### 7.1 指定ルール

1. 企業をチェックし、その企業配下の事業所を**1つも選ばなかった場合** → その企業まるごと（配下すべて）が担当範囲になる。
2. 企業をチェックし、その企業配下の事業所を**1つ以上選んだ場合** → 企業まるごとの権限は付与されず、**選んだ事業所（＋その事業所配下で選んだ部署）だけ**に絞られる。この場合、企業チェックは「配下の事業所・部署を選ぶための入口」という位置づけになる。
3. 事業所は、チェックした企業の配下のものしか選べない。
4. 部署は、選んだ事業所の配下のものしか選べない。
5. 企業をまたいだ事業所、事業所をまたいだ部署の追加担当はできない（親子関係を必ず満たす）。
6. 担当範囲は**1つの健保の範囲内**に収める必要がある。複数健保にまたがる指定はエラー（ブロック）。
7. 指定できるのは、**発行者自身が操作できる範囲内**のものだけ。範囲外の指定はエラー（ブロック）。
8. `company_user` の所属健保は、担当範囲に指定した企業／事業所／部署から自動的に決まる。
9. 企業を1つも選ばず、他社の事業所・部署だけを担当範囲にすることもできる（ルール1〜8を満たす範囲で）。

### 7.2 担当範囲と加入者の可視性

- `company_user` は、加入者が「担当範囲に指定したいずれかの企業・事業所・部署に属している」場合にのみ、その加入者を閲覧・操作できる。

## 8. アカウントの状態

| 状態キー | 表示名 | ログイン | 説明 |
|---|---|---|---|
| `invited` | PW未設定 | 不可 | 発行直後。本人がパスワードを設定するまでこの状態 |
| `active` | 有効 | 可 | 通常利用中 |
| `disabled` | 無効 | 不可 | 一時停止。再度有効化できる |
| `deleted` | 削除済み | 不可 | 論理削除。一覧では末尾に淡色表示。復元不可 |

### 8.1 状態遷移

- `invited` → `active` … 本人がパスワードを設定
- `active` / `invited` → `disabled` … 管理者による無効化
- `disabled` → `active` … 再有効化（パスワード設定済みの場合）
- `disabled` → `invited` … 再有効化（パスワード未設定の場合）
- 任意 → `deleted` … 管理者による論理削除（パスワード・各種トークンを消去）
- `deleted` → （レコード物理削除） … 管理者による「完全削除」

## 9. アカウント登録の流れ

```
[登録画面]
  ・メールアドレス（ログインID）
  ・利用者名
  ・代表者アカウントか否か
  ・ロール
  ・CSVダウンロード許可の有無
  ・（company_user の場合）担当範囲（健保 → 企業 → 事業所・部署 の順で選択）
        ↓ 入力検証・閲覧範囲の自動決定
[確認画面]
  ・入力内容の確認
  ・このアカウントが閲覧できることになる加入者の
    「件数」「企業数・事業所数」「内訳」「サンプル一覧」を提示
        ↓ 確認チェックを経て発行
[発行]
  ・状態 = invited
  ・招待トークンを発行（有効期限 72 時間）
  ・初期パスワードは発行しない（本人が設定する）
        ↓
[一覧画面へ戻り、「案内リンク送信」モーダルを自動表示]
```

### 9.1 登録時の必須検証

- メールアドレスの形式が正しいこと。
- メールアドレスが既存アカウントと重複しないこと（重複相手が `deleted` の場合は「完全削除してから再登録」を促す）。
- 利用者名が入力されていること。
- 指定ロールが発行可能ロールに含まれること。
- `company_user` の場合、担当範囲が1件以上指定されていること。
- `company_user` の担当範囲が単一健保に収まっていること。
- `kenpo_user` を `system_admin` が発行する場合、所属健保が選択されていること（他ロールが発行する場合は発行者の健保を自動継承）。

## 10. 初期パスワードの受け渡し（3方式）

メールが使えない現場を想定し、次の3方式を用意する。

| 方式 | 内容 |
|---|---|
| 案内メール送信 | パスワード設定用リンクを記載したメールを本人へ送信。リンク期限切れなら自動で再発行してから送信 |
| 案内リンクの画面表示 | 設定用リンクを画面に表示し、口頭・社内チャット等で本人へ伝える。期限切れなら新リンクを発行 |
| 管理者による直接設定 | 管理者がその場でパスワードを設定（自動生成 または 手入力）。メールは送信しない |

- 招待リンクの有効期限：**72時間**。
- 招待リンクは**1回のみ有効**。本人がパスワードを設定すると無効化される。
- メールにパスワードは含めない。

## 11. アカウント編集の流れ

```
[編集画面]  … 変更可能項目：
  ・利用者名
  ・ロール
  ・所属健保（system_admin が kenpo_user を編集する場合のみ）
  ・担当範囲（company_user）
  ・CSVダウンロード許可
  ・代表者フラグ
  （メールアドレス＝ログインID は変更不可）
        ↓ 入力検証・閲覧範囲の再決定
[確認画面]
  ・変更前 → 変更後 の差分一覧
  ・変更前後で「閲覧できる加入者数」がどう変わるかを提示
  ・閲覧範囲が拡大する場合は警告
        ↓ 確認チェックを経て保存
[保存]
  ・変更があれば本人へ「設定変更のお知らせ」メールを自動送信
    （変更内容・変更後の閲覧範囲を記載。パスワードは変わらない旨を明記）
```

### 11.1 編集の制約

- **自分自身のアカウントは編集できない**（ロール等の変更は別の管理者へ依頼する運用）。
- `deleted` のアカウントは編集できない。
- 変更後のロール・担当範囲も、登録時と同じ検証（発行可能ロール・単一健保・発行者の操作範囲内）を満たすこと。

## 12. 無効化・削除・完全削除

| 操作 | 対象 | 挙動 |
|---|---|---|
| 無効化 / 再有効化 | 自分以外 | `disabled` ⇔ `active` / `invited` をトグル |
| 削除（論理） | 自分以外、`deleted` 以外 | 状態を `deleted` に変更。パスワード・各種トークンを消去。ログイン不可。**復元不可** |
| 完全削除 | `deleted` のアカウントのみ | レコードを物理削除。**確認欄にメールアドレスの完全一致入力を要求**。監査ログの記録は残す。同一メールアドレスの再登録が可能になる |

- 自分自身に対する無効化・削除・完全削除・パスワード設定はできない。

## 13. パスワード仕様

### 13.1 ポリシー

- 12文字以上。
- 英字を1文字以上、数字を1文字以上含む。
- 確認用入力と一致すること。

### 13.2 自動生成パスワード

- 誤読しにくい文字のみ使用（`0/O`、`1/l/I` などを除外）。
- 14文字程度。上記ポリシーを必ず満たす。

### 13.3 本人によるパスワード再設定

```
[ログイン画面の「パスワードをお忘れの方」]
        ↓ メールアドレス入力
[再設定用トークンを発行（有効期限 2 時間）／メール送信]
        ↓ メール内リンク
[新パスワード設定画面] → 設定完了で active、ログインへ
```

- 対象は `active` または `invited` のアカウントのみ。
- **アカウントの存在有無を画面表示で区別しない**（存在しないメールでも「送信しました」と同じ応答。アカウント列挙対策）。
- 再設定リンクは1回のみ有効。有効期限 **2時間**。

### 13.4 管理者によるパスワード設定

- 対象アカウントを操作する権限がある管理者のみ実行可能。
- 設定後、状態は `active` になり、招待・再設定トークンは消去される。
- メール送信は行わない。

## 14. 管理権限マトリクス（誰が誰を操作できるか）

| 操作者 | 操作できる対象アカウント |
|---|---|
| `system_admin` | すべてのアカウント |
| `kenpo_user` | 自分と同じ健保に所属し、かつロールが `system_admin` でないアカウント |
| `company_user` | ロールが `company_user` で、かつ**対象の担当企業が自分の担当企業の部分集合**であるアカウント（対象の担当企業が空の場合は操作不可） |

一覧画面に表示される範囲も上記に準じる。

| 操作者 | 一覧に表示される範囲 |
|---|---|
| `system_admin` | 全アカウント |
| `kenpo_user` | 自健保のアカウント（`system_admin` を除く） |
| `company_user` | 自分の担当企業に属する `company_user` アカウント |

## 15. アカウント一覧・検索・エクスポート

### 15.1 一覧の表示項目

利用者名（代表者バッジ）／メールアドレス／ロール／閲覧範囲／所属健保／担当企業・事業所・部署／CSVダウンロード可否／状態／登録日／最終ログイン日時／操作ボタン。

- `deleted` の行は淡色で一覧末尾に表示。
- 代表者アカウントは一覧上部に優先表示。

### 15.2 検索・絞り込み

- 利用者名・メールアドレス・所属企業名：部分一致の即時フィルタ（入力補完サジェスト付き、検索ボタン不要）。
- 所属健保・ロール・状態：選択式フィルタ。
- 検索は一覧画面上で完結する。

### 15.3 行ごとの操作ボタン

| 状態 | 表示されるボタン |
|---|---|
| `invited` / `active` | 案内リンク表示 / パスワード設定 / 編集 / 削除 |
| `disabled` | 編集 / 削除 |
| `deleted` | 完全削除 |
| 自分自身の行 | 「自分のアカウント」表示のみ（操作不可） |

### 15.4 CSVエクスポート

- 一覧の内容をCSV出力できる（`deleted` を除く）。出力範囲は操作者の可視範囲に準じる。

## 16. 代表者アカウント

## 17. CSVダウンロード権限

# 第3部　横断要件

## 21. 監査ログ（操作ログ）

### 21.1 基本要件

- **追記専用**。更新・削除は禁止（アプリからもデータ層からも変更不可とする）。
- アカウントを物理的に完全削除しても、そのアカウントに関する操作ログは残す。

### 21.2 記録項目

日時／利用画面系統／カテゴリ／操作内容／結果／実行者メールアドレス／実行者ロール／対象健保／接続元IPアドレス／操作対象／詳細。

- カテゴリ例：認証／アカウント／マスタ／取込／ダウンロード
- 結果：成功 / 失敗 / ブロック

### 21.3 記録対象イベント

- **認証**：ログイン成功・失敗（失敗理由：アカウント不存在／PW未設定／無効・削除済み／PW不一致）、ログアウト、本人によるパスワード再設定の申請・実行
- **アカウント**：発行、権限変更（変更差分を詳細に記録）、設定変更通知メール送信、案内リンク表示・案内メール送信・期限切れリンク再発行、管理者によるパスワード設定、状態変更（有効化・無効化）、削除、完全削除、各種ブロック
- **マスタ**：健保・企業・事業所・部署・加入者の登録・編集・削除、スコープ外操作のブロック
- **取込**：取込ファイルの検証、確定（件数・ファイル名）
- **ダウンロード**：CSV出力、上限超過によるブロック
- **アクセス制御**：権限不足によるアクセス拒否、許可外接続元の拒否

### 21.4 ログの閲覧範囲

| 操作者 | 閲覧できるログ |
|---|---|
| `system_admin` | 全ログ |
| `kenpo_user` | 自健保に関するログ ＋ 自分が実行者のログ |
| `company_user` | 自分の担当企業に属するアカウントが実行者となったログ |

- ログ画面では、カテゴリ・利用画面系統・キーワード・期間で絞り込み、CSVエクスポートができる。

## 22. 認証・接続制御

- パスワードは**ハッシュのみ保存**。画面に元の値を表示しない。
- 接続元IPアドレスの許可範囲を設定できる。範囲外からのアクセスは全画面で拒否し、監査ログに記録する。
- ログイン成功時に最終ログイン日時を記録する。
- ログイン後は、アカウントのロールに応じた画面（総合管理／健保管理）へ自動的に遷移する。利用者が画面を選ぶ必要はない。

## 23. 本番化に向けた宿題（現行モックアップの未対応事項）

- HTTPS 化。
- 多要素認証（MFA）。

# 付録B　設計上の意図（要件化の際の判断材料）

- **識別コードは先方の番号を正とし、システムは照合キーとして保持する。** 内部コードは表示専用。これにより取込の冪等性（同じファイルの再取込で重複しない）と、順序非依存（加入者先行取込→後追い紐づけ）が成立する。
- **閲覧範囲は人手で設定させず、ロールと組織選択から必ず導出する。** 権限の付け間違いを防ぐため。
- **アカウント発行・変更の前に、必ず「そのアカウントが見られるようになる加入者」を件数と内訳で提示する。** 範囲の過大付与に気づけるようにするため。
- **「企業をチェックしても、配下の事業所を1つでも選ぶと企業全体権限が外れる」挙動**は直感に反しやすいため、本番実装ではUI上に明示的なガイドを置くことを推奨。
- **監査ログは改ざん不可・完全削除耐性**（アカウントを消してもログは残る）を要件とする。
